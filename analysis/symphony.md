# OpenAI Symphony: analysis for the Tailrocks manager / task system

Analysis date: 2026-08-27. Sources: a `git clone --depth 50` of
https://github.com/openai/symphony (HEAD `8001b52`, "Scrub GitHub and GitLab authentication token
aliases (#119)"), GitHub metadata via `gh`, OpenAI's announcement post and third-party write-ups.
Repo-relative file paths below refer to that clone. Where a claim comes only from documentation or
the announcement (not from code), this is called out explicitly.

## 1. Identity

- **What**: "Symphony turns project work into isolated, autonomous implementation runs, allowing
  teams to manage work instead of supervising coding agents" (`README.md`, GitHub description).
  It is primarily a **language-agnostic specification** (`SPEC.md`, "Status: Draft v1") plus an
  "experimental reference implementation" in Elixir/OTP (`elixir/`). The README's "Option 1" is
  literally "Tell your favorite coding agent to build Symphony in a programming language of your
  choice" from the spec (`README.md`).
- **By whom**: OpenAI. The announcement post lists Alex Kotliarskyi, Victor Zhu and Zach Brock as
  authors (https://openai.com/index/open-source-codex-orchestration-symphony/, fetched via a
  reader proxy; the direct URL returns 403 to non-browser clients). Commit authorship in the
  clone's last 50 commits is dominated by Alex Kotliarskyi (31 of 50), with small contributions
  from OpenAI staff (`git log --format='%an' | sort | uniq -c`). The announcement states "Every
  line in our project repository had to be generated by Codex."
- **When**: repository created 2026-02-26 (`gh repo view --json createdAt`); public
  announcement 2026-04-27/28 (OpenAI post; https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/);
  releases `v0.0.1` 2026-07-18 and `v0.0.2` 2026-07-24 (`gh release list`); last push
  2026-08-19. The clone's 50-commit window spans 2026-03-04 to 2026-08-12.
- **License**: Apache-2.0 (`LICENSE`, `NOTICE`).
- **Language**: Elixir 1.19 / OTP 28 via `mise` (`elixir/AGENTS.md`, `elixir/mise.toml`).
  Phoenix 1.8 + LiveView 1.1 + Bandit for the optional web UI, `req` for HTTP, `yaml_elixir`,
  `solid` (Liquid templates), `ecto` (config schema only, no DB), `burrito` for self-contained
  binaries (`elixir/mix.exs` lines 72-85).
- **Size / maturity**: ~12.6k lines of Elixir under `elixir/lib` (`wc -l`), 21 test files with
  ~267 `test` blocks (`elixir/test/symphony_elixir/`). GitHub: 26,882 stars, 2,756 forks
  (`gh repo view`, 2026-08-27). **Issues are disabled** on the repo (`gh issue list` →
  "has disabled issues"); PRs are accepted (PR #83 "feat(jira): add claim lease support" open;
  #102-#119 merged in July-August 2026). The README labels it "a low-key engineering preview for
  testing in trusted environments"; `elixir/README.md` says "prototype software intended for
  evaluation only ... We recommend implementing your own hardened version based on `SPEC.md`."
  The announcement (per Help Net Security) says OpenAI "does not plan to maintain Symphony as a
  standalone product." Third-party derivatives exist, e.g. `cskwork/oh-my-symphony`
  (multi-agent fork driving Codex, Claude Code, Gemini, Pi CLIs; https://github.com/cskwork/oh-my-symphony).

## 2. Goal and problem statement (their words)

`SPEC.md` §1: "Symphony is a long-running automation service that continuously reads work from a
configured issue tracker, creates an isolated workspace for each issue, and runs a coding agent
session for that issue inside the workspace." It "solves four operational problems": turning issue
execution into "a repeatable daemon workflow instead of manual scripts"; isolating agent execution
in per-issue workspaces; keeping "the workflow policy in-repo (`WORKFLOW.md`)"; and providing
"enough observability to operate and debug multiple concurrent agent runs."

The announcement frames the bottleneck as humans: "Most people could comfortably manage three to
five sessions at a time before context switching became painful." The core principle: "For every
open task, guarantee that an agent is running in its own workspace." Zach Brock (quoted at
https://tessl.io/blog/openai-open-sources-symphony-a-spec-for-orchestrating-codex-agents):
"Giving coding agents access to task-tracking and changing their goal to 'convince a human to
merge this code' is the clear next phase of software engineering." Claimed result: "Among some
teams at OpenAI, we saw the number of landed PRs increase by 500% in the first three weeks"
(announcement; not reproducible from the repo).

Explicit boundary (`SPEC.md` §1): "Symphony is a scheduler/runner and tracker reader. Ticket
writes (state transitions, comments, PR links) are typically performed by the coding agent through
provider-native tools executed by Symphony". Non-goals (§2.2): "Rich web UI or multi-tenant
control plane", "General-purpose workflow engine or distributed job scheduler", "Built-in business
logic for how to edit tickets, PRs, or comments", "Mandating strong sandbox controls beyond what
the coding agent and host OS provide."

## 3. Architecture

### Components (spec §3.1, mirrored 1:1 in code)

| Spec component | Elixir module | Notes |
|---|---|---|
| Workflow Loader | `elixir/lib/symphony_elixir/workflow.ex`, `workflow_store.ex` | Parses `WORKFLOW.md` front matter + prompt body; `WorkflowStore` GenServer polls the file every 1 s (`@poll_interval_ms 1_000`) by mtime/size/hash and hot-reloads, keeping the "last known good" config on error. |
| Config Layer | `config.ex`, `config/schema.ex` | Ecto embedded schemas for typed validation; defaults live in the schema (e.g. `polling.interval_ms` 30 000, `agent.max_concurrent_agents` 10, `agent.max_turns` 20, `codex.turn_timeout_ms` 3 600 000, `codex.stall_timeout_ms` 300 000). |
| Issue Tracker Adapter | `tracker.ex` (behaviour), `linear/`, `github/`, `jira/`, `asana/`, `gitlab/`, `tracker/memory.ex` | Behaviour with two read callbacks plus optional agent-tool callbacks. |
| Orchestrator | `orchestrator.ex` (~1 990 lines, one GenServer) | Owns poll tick, `running`/`claimed`/`blocked`/`retry_attempts` maps, dispatch, reconciliation, retry timers, token totals. |
| Workspace Manager | `workspace.ex` | Per-issue dirs, hooks, path safety, local or over SSH. |
| Agent Runner | `agent_runner.ex`, `codex/app_server.ex` | Spawns `codex app-server` as a port (local `bash -lc` or `ssh`), JSON-RPC over stdio, multi-turn loop. |
| Status Surface | `status_dashboard.ex` (terminal TUI), `symphony_elixir_web/*` (Phoenix LiveView + JSON API) | Optional. |
| Logging | `log_file.ex`, `elixir/docs/logging.md` | File logs under `--logs-root` (default `./log`). |

Supervision: `agent_runtime_supervisor.ex` runs a `Task.Supervisor` and the `Orchestrator` under
`:one_for_all`, so an orchestrator crash also tears down all in-flight agent tasks (the code
comment: "Supervises the scheduler authority together with its agent tasks").

### How it runs

A single long-running daemon process: `./bin/symphony [--logs-root <path>] [--port <port>]
[path-to-WORKFLOW.md]` (`elixir/lib/symphony_elixir/cli.ex` line 81; `elixir/README.md` "Run").
Burrito ships self-contained binaries for macOS/Linux arm64/x86_64 that "still expect `codex`,
`git`, and the selected tracker credentials on the target machine" (`elixir/README.md`,
`.github/workflows/burrito-release.yml`).

### Single host vs. distributed

Default is single host: orchestrator and all agent subprocesses run on the machine where
Symphony starts. An **optional SSH worker extension** (`SPEC.md` Appendix A; code in `ssh.ex`,
`workspace.ex`, `codex/app_server.ex` `start_port/3` with a `worker_host`) keeps "one central
orchestrator but executes worker runs on one or more remote hosts over SSH". Config:
`worker.ssh_hosts` (list) and `worker.max_concurrent_agents_per_host` (`config/schema.ex`
lines 124-141). The orchestrator picks the least-loaded host, prefers the previous host on retry,
and waits when all hosts are at capacity rather than falling back to local (`orchestrator.ex`
`select_worker_host/2`, lines ~1281-1341). `workspace.root` "is interpreted on the remote host"
(Appendix A.1). The live E2E test spins up two SSH worker containers with `docker compose`
(`elixir/test/support/live_e2e_docker/Dockerfile`, `docker-compose.yml`): `node:20-bookworm-slim`
+ `openssh-server` + `npm install --global @openai/codex`, mounting the host `~/.codex/auth.json`.
There is **no** container-per-task in the product itself; containers appear only in the test rig.

### Storage

There is no database. `SPEC.md` §2.1: "Support tracker/filesystem-driven restart recovery without
requiring a persistent database; exact in-memory scheduler state is not restored." §14.3: "Current
design is intentionally in-memory for scheduler state ... No retry timers are restored ... No
running sessions are assumed recoverable." Durable state is (a) the tracker (issue state,
comments, attachments), (b) per-issue workspace directories on disk (preserved across runs,
`SPEC.md` §9.1), and (c) log files. `elixir/README.md` confirms: "Blocked entries are in memory
only; restarting the orchestrator clears that blocked map."

## 4. Task model

### What is a task

The unit is a tracker **issue**, normalised into `SymphonyElixir.Tracker.Issue`
(`elixir/lib/symphony_elixir/tracker/issue.ex`): `id` (opaque dispatch identity), `native_ref`,
`identifier` (human key, e.g. `MT-620`, must be unique because it names the workspace), `title`,
`description`, `priority`, `state`, `branch_name`, `url`, `assignee_id`, `labels`, `blocked_by`
(list of `{id, identifier, state}`), `dispatchable` (adapter-derived boolean), `created_at`,
`updated_at`. `SPEC.md` §4.1.1 says the name is generic: "an adapter MAY map it from a ticket,
card, project item, or another provider-native work object."

### Where work comes from

Exclusively from an external tracker, polled on a cadence (`polling.interval_ms`, default 30 s in
schema, 5 s in the repo's own `elixir/WORKFLOW.md`). Adapters shipped in code: Linear (original),
GitHub Issues, Jira Cloud, Asana, GitLab Issues, plus an in-memory test adapter (`tracker.ex`
`@adapters` map). There is no file-based or API-based work intake. Humans "provide work" by
creating issues and moving them into an active state. The repo's own workflow uses Linear states
`Backlog` (ignored), `Todo`, `In Progress`, `Human Review`, `Merging`, `Rework`, `Done`; the
README notes "Rework", "Human Review", and "Merging" are non-standard Linear statuses you must
create (`elixir/README.md` "How to use it").

An opt-in label gate exists: `tracker.required_labels` — "an issue must have every configured
label to dispatch or continue running" (`elixir/README.md`; `Issue.routable?/2`). PR #88
"[linear] Require opt-in labels for dispatch" added it.

### Status lifecycle

Two separate state machines:

1. **Tracker states** (workflow-defined): configured as `tracker.active_states` and
   `tracker.terminal_states`. Symphony dispatches issues whose state is in `active_states`, stops
   agents and deletes workspaces when an issue reaches a terminal state, and stops agents (without
   cleanup) when an issue moves to any other non-active state (`orchestrator.ex`
   `reconcile_issue_state/4`, lines 421-441). Transitions between tracker states are made **by the
   agent** via tracker tools, per the prompt (see §6).
2. **Orchestrator claim states** (`SPEC.md` §7.1): `Unclaimed` → `Claimed` → `Running` /
   `RetryQueued` → `Released`; plus a `blocked` map for input-required sessions added in the Elixir
   implementation (`orchestrator.ex` `State` struct). Run attempt phases (§7.2):
   `PreparingWorkspace`, `BuildingPrompt`, `LaunchingAgentProcess`, `InitializingSession`,
   `StreamingTurn`, `Finishing`, `Succeeded`, `Failed`, `TimedOut`, `Stalled`,
   `CanceledByReconciliation`.

Key nuance (`SPEC.md` §7.1): "A successful worker exit does not mean the issue is done forever."
While the issue stays in an active state the worker loops turns on the same Codex thread up to
`agent.max_turns`; after the worker exits normally the orchestrator schedules a 1 s "continuation
retry" and re-dispatches if the issue is still active (`agent_runner.ex` `do_run_codex_turns/8`;
`orchestrator.ex` `handle_agent_down(:normal, ...)` lines 208-224). So "one agent per task" means
"an agent is always running while the ticket is active" — even in `Human Review`, if that state is
listed as active (the repo's `WORKFLOW.md` lists `Todo`, `In Progress`, `Merging`, `Rework` as
active and deliberately omits `Human Review`, so no agent burns tokens waiting on humans).

### Dependencies

Declared in the tracker, not in Symphony config. `SPEC.md` §4.1.1 calls `blocked_by` "best-effort
provider metadata" and requires adapters to fold blocker semantics into the `dispatchable`
boolean because "the generic scheduler cannot infer [them] safely." Concretely:

- Linear: blockers come from `inverseRelations` of type `blocks`
  (`elixir/lib/symphony_elixir/linear/client.ex` lines 35, 80, 618). An issue in `Todo` is
  `dispatchable` only if no blocker is in a non-terminal state (`blocked_before_dispatch?/2`,
  lines 500-512). Once the issue is `In Progress`, blockers are no longer checked.
- Jira: blockers from issue links; gate applies only while the status category is `new` (or status
  `To Do`) (`jira/client.ex` lines 337-353; PR #108 "honor blocking issue links", #113 "Gate Jira
  new-category issues on blockers").
- GitHub/GitLab/Asana: `blocked_by: []`; GitHub marks pull requests non-dispatchable
  (`github/client.ex` lines 198-199).

The orchestrator itself never reasons about a DAG; there is no topological scheduling, only
"skip if adapter says not dispatchable." Dependencies are thus a **soft gate at dispatch time**,
re-evaluated each poll.

### Priority

`priority` integer 1..4 sorts first, then `created_at` oldest-first, then identifier
(`orchestrator.ex` `sort_issues_for_dispatch/1`, lines 796-814; `SPEC.md` §8.2).

### Who decomposes

Humans, in the tracker. Symphony has no planner/decomposer. The workflow prompt instructs the
agent to file **follow-up issues** for out-of-scope work: "file a separate Linear issue ... be
placed in `Backlog` ... link the current issue as `related`, and use `blockedBy` when the
follow-up depends on the current issue" (`elixir/WORKFLOW.md` "Default posture"). Because
`Backlog` is not an active state, agent-created issues never auto-dispatch until a human promotes
them to `Todo`. That is the only decomposition mechanism, and it is prompt-only.

## 5. Execution model

### Spawning

Per poll tick, for each eligible issue with a free slot, the orchestrator starts a
`Task.Supervisor` child running `AgentRunner.run/3` and monitors it (`orchestrator.ex`
`spawn_issue_on_worker_host/5`, lines 953-1004). `AgentRunner` creates/reuses the workspace, runs
the `before_run` hook, starts one `codex app-server` process, then loops turns
(`agent_runner.ex` lines 38-140).

### Isolation

- **Filesystem**: one directory per issue at `<workspace.root>/<workspace_key>` where
  `workspace_key` is the identifier with non-`[A-Za-z0-9._-]` chars replaced by `_` plus a
  16-hex-char SHA-256 suffix if sanitisation changed anything (`workspace.ex` `workspace_key/1`,
  lines 481-503). Three invariants (`SPEC.md` §9.5): agent cwd == workspace path; workspace path
  under workspace root (symlink-escape checks via `PathSafety.canonicalize`); sanitised key.
  `elixir/AGENTS.md`: "Never run Codex turn cwd in source repo."
- **Population**: not built in. `hooks.after_create` (runs once on fresh dir) is where you
  `git clone ... .`; the repo's own workflow does `git clone --depth 1 https://github.com/openai/symphony .`
  then `mix deps.get` (`elixir/WORKFLOW.md`). Workspaces are full clones, **not git worktrees**,
  and are preserved after successful runs (`SPEC.md` §9.1) and deleted on terminal state.
- **Process sandbox**: delegated entirely to Codex. Defaults in code
  (`config/schema.ex` lines 181-197): `approval_policy` =
  `{"reject": {"sandbox_approval": true, "rules": true, "mcp_elicitations": true}}`,
  `thread_sandbox` = `workspace-write`, `turn_sandbox_policy` = `workspaceWrite` rooted at the
  issue workspace with `networkAccess: false`. The repo's own workflow overrides to
  `approval_policy: never` and `networkAccess: true`. No containers, cgroups, or OS users are
  created by Symphony; `SPEC.md` §15.5 lists "OS/container/VM sandboxing" as optional hardening
  the deployer should add.
- **Hooks are not sandboxed**: "Hooks are fully trusted configuration" (`SPEC.md` §15.4). They
  run `sh -lc <script>` with the orchestrator's privileges (`workspace.ex` line 620).

### One agent per task, concurrency

Yes, exactly one Codex session per issue at a time, enforced by `claimed`/`running` sets
(`orchestrator.ex` `should_dispatch_issue?/4`, lines 816-829). Limits: `agent.max_concurrent_agents`
(global, default 10), `agent.max_concurrent_agents_by_state` (per tracker state, e.g. cap
`Merging` at 1), `worker.max_concurrent_agents_per_host` (SSH). There are **no CPU/memory/token
budgets** per task; the only per-run bounds are timeouts (`turn_timeout_ms` = silence timeout
during a turn, `stall_timeout_ms` = orchestrator-side inactivity kill, `hooks.timeout_ms`) and
`max_turns`.

### Runtime supported

Codex only. `SPEC.md` §3.3 requires a "Coding-agent executable that supports the targeted Codex
app-server mode" and §10 is written against the Codex app-server JSON-RPC protocol
(`initialize`, `thread/start`, `turn/start`, `turn/completed`, `item/tool/call`,
`item/commandExecution/requestApproval`; `codex/app_server.ex`). `codex.command` is a free-form
shell string, so any binary that speaks that protocol works, but nothing else is abstracted. The
fork `oh-my-symphony` is what you reach for if you want Claude Code / Gemini.

### Prompt / brief given to the agent

The Markdown body of `WORKFLOW.md` is a Liquid template rendered with `issue` and `attempt`
(`prompt_builder.ex`; strict variables/filters). First turn gets the full rendered prompt;
continuation turns on the same thread get only a short "Continuation guidance" block
(`agent_runner.ex` lines 142-154). The reference `elixir/WORKFLOW.md` is ~330 lines of policy:
status map, "Step 0 determine state and route", a persistent `## Codex Workpad` comment as
"the source of truth for progress" with Plan / Acceptance Criteria / Validation / Notes /
Confusions sections, a mandatory "PR feedback sweep protocol", a "blocked-access escape hatch",
a "Completion bar before Human Review", and a "Rework" flow that closes the PR, deletes the
workpad and restarts from `origin/main`.

Repo context beyond the clone: whatever `AGENTS.md`/skills live in the cloned repo. Symphony
ships Codex skills under `.codex/skills/` (`commit`, `push`, `pull`, `land`, `linear`, `debug`,
`release`) that the README suggests copying into your repo.

### Tracker access from the agent

Symphony injects **provider-native dynamic tools** into the Codex session (`linear_graphql`,
`github_api`, `jira_rest`, `asana_api`, `gitlab_api`) and executes them host-side with the
orchestrator's credential, while **stripping** the token env vars from the Codex child
(`codex/app_server.ex` `tracker_secret_port_env/1`, `tracker_secret_unset_command/1`;
`tracker.ex` `bind_agent_tools/0`). Tool binding is snapshotted per session so a hot reload cannot
make "an in-flight session advertise one provider and execute another" (`SPEC.md` §10.5).

## 6. Verification and completion

### How "done" is determined

Symphony **does not verify anything itself**. Done-ness is a tracker state transition performed by
the agent. `SPEC.md` §1: "A successful run can end at a workflow-defined handoff state (for
example `Human Review`), not necessarily `Done`." The orchestrator's notion of success is only
"the Codex turn completed and the issue is no longer in an active state."

Quality gates live in the prompt and in the repo's own CI:

- Prompt (`elixir/WORKFLOW.md` "Completion bar before Human Review"): workpad checklist complete;
  "Validation/tests are green for the latest commit"; PR feedback sweep clean; "PR checks are
  green, branch is pushed, and PR is linked on the issue"; `symphony` label present. Any
  ticket-authored `Validation`/`Test Plan`/`Testing` section is "non-negotiable acceptance input."
- Repo CI (`.github/workflows/make-all.yml` runs `make all`: format, credo lint, coverage,
  dialyzer; `pr-description-lint.yml` enforces `.github/pull_request_template.md` via
  `mix pr_body.check`; `mix specs.check` enforces `@spec` on public functions).
- The `land` skill (`.codex/skills/land/SKILL.md`) waits for `gh pr checks --watch`, for
  "Codex Review" bot comments, and for human review comments before `gh pr merge --squash`.

The demo video description adds "proof of work: CI status, PR review feedback, complexity
analysis, and walkthrough videos" (`README.md`); of these only CI and PR feedback appear in the
shipped workflow; "walkthrough videos" is referenced by the `linear` skill's `fileUpload` recipe
and by prompt lines mentioning `launch-app`/`github-pr-media` skills that are **not in this repo**.

### Trust model for verification

Verification is trusted because a **human** reviews the PR: the `Human Review` state exists
precisely so the agent stops and waits. The agent self-reports validation in the workpad; nothing
in Symphony checks the claim. `SPEC.md` §15.5 warns against assuming "tracker data, repository
contents, prompt inputs, or tool arguments are fully trustworthy."

### Retry on failure

`orchestrator.ex` / `SPEC.md` §8.4:

- Normal worker exit → continuation retry after 1 000 ms (`@continuation_retry_delay_ms`).
- Abnormal exit, spawn failure, stall, turn failure, hook failure → exponential backoff
  `min(10000 * 2^(attempt-1), agent.max_retry_backoff_ms)` (default cap 5 min), attempt counter
  capped at power 10 (`failure_retry_delay/1`, lines 1240-1243). **There is no max attempt
  count**; retries continue as long as the issue stays active. Each retry re-fetches the issue and
  releases the claim if it left the active states.
- Stall: if no Codex event for `stall_timeout_ms` (default 5 min) the worker is killed and requeued
  (`reconcile_stalled_running_issues/1`).
- Workspace is reused across retries; the template gets `attempt` so the prompt says "Resume from
  the current workspace state instead of restarting from scratch" (`elixir/WORKFLOW.md`).

### Escalation to humans

Three channels, all indirect:

1. **Tracker state**: the prompt's "blocked-access escape hatch" tells the agent to move the
   ticket to `Human Review` with a "blocker brief" in the workpad when a required non-GitHub tool
   or credential is missing.
2. **Blocked map**: if Codex emits an approval request while `approval_policy != never`, a
   `turn/input_required`, or an MCP elicitation, the Elixir orchestrator marks the issue
   `blocked` (kept claimed, agent stopped, shown in TUI/JSON/dashboard) instead of retrying
   (`orchestrator.ex` `input_required_blocker?/1`, `block_issue_from_entry/4`; `elixir/README.md`).
   Cleared only by restarting or by the issue leaving active states. With `approval_policy: never`
   (the repo's own setting) all approvals are auto-accepted (`app_server.ex`
   `auto_approve_requests: session_policies.approval_policy == "never"`).
3. **Operator levers** (`SPEC.md` §14.4): edit `WORKFLOW.md` (hot reload), change issue state in
   the tracker (terminal → kill + clean; non-active → kill, keep workspace), restart the service.

No notifications (Slack, email, webhooks) exist in code.

## 7. Integration of results

Entirely delegated to the agent + GitHub. Symphony has no git logic beyond what hooks run.

- Branching: the agent creates a branch (Linear supplies `branch_name`), commits via the `commit`
  skill, pushes via `push`, and attaches the PR to the issue via `attachmentLinkGitHubPR`
  (`.codex/skills/linear/SKILL.md`).
- Keeping current: the `pull` skill merges `origin/main` (merge, not rebase; `zdiff3` conflict
  style; `rerere` enabled) and includes ~60 lines of conflict-resolution guidance; asking the user
  is reserved for product-intent conflicts (`.codex/skills/pull/SKILL.md`).
- Merge: only when a human moves the ticket to `Merging`; the `land` skill loops: check
  mergeability, pull/resolve, wait for CI, address Codex/human review comments (every comment must
  be "accept, clarify, or push back" with a `[codex]`-prefixed reply), then squash-merge, then the
  agent moves the ticket to `Done` (`elixir/WORKFLOW.md` Step 3; `.codex/skills/land/SKILL.md`).
- Parallel results: N agents produce N independent PRs against `main`; conflicts are handled
  serially by whichever PR lands later, by the agent, during `pull`/`land`. There is no
  integration branch, no merge queue, no cross-task coordination. The repo's own config caps
  concurrency by state (`max_concurrent_agents_by_state`) which is the documented way to
  serialise `Merging`.

## 8. Observability and UI

- **Terminal dashboard** (`status_dashboard.ex`; enabled by default, `observability.dashboard_enabled`):
  agents used/max, tokens/s sparkline, aggregate runtime, in/out/total tokens, Codex rate limits,
  project URL, a "Running" table (ID, stage, PID, age/turn, tokens, session, last event) and a
  "Backoff queue" (see `elixir/test/fixtures/status_dashboard_snapshots/super_busy.snapshot.txt`).
- **Web dashboard + JSON API** (`--port` or `server.port`; `symphony_elixir_web/router.ex`):
  LiveView at `/`, `GET /api/v1/state`, `GET /api/v1/<issue_identifier>`, `POST /api/v1/refresh`
  (forces a poll). Binds `127.0.0.1` by default. No auth.
- **Logs**: file sink under `--logs-root`; conventions in `elixir/docs/logging.md` require
  `issue_id`, `issue_identifier`, `session_id` (`<thread_id>-<turn_id>`) on lifecycle lines.
- **Token accounting**: `elixir/docs/token_accounting.md` explains preferring absolute
  `thread/tokenUsage/updated.total` over deltas to avoid double counting.
- **No** notifications, alerting, persistence of history, or per-task log viewer; the tracker
  workpad comment is the human-facing progress record.

## 9. Configuration

Single file `WORKFLOW.md`: YAML front matter (config) + Markdown body (prompt). Top-level keys in
code (`config/schema.ex`): `tracker`, `polling`, `workspace`, `worker`, `agent`, `codex`, `hooks`,
`observability`, `server`. `$VAR` indirection for secrets/paths; `~` expansion; relative
`workspace.root` resolves relative to the `WORKFLOW.md` directory (`SPEC.md` §6.1). Reload is
live (1 s poll) for everything except HTTP listener settings.

Reference example (`elixir/WORKFLOW.md`, abridged):

Extension points:

- New tracker: implement the `SymphonyElixir.Tracker` behaviour (`fetch_issues_by_states/1`,
  `fetch_issues_by_ids/1`, optional `agent_tool_specs/0`, `execute_agent_tool/3`,
  `secret_environment_names/1`, `validate_config/1`) and register in `@adapters`
  (`tracker.ex`). Each adapter must publish a documented "profile" (`SPEC.md` §11.2).
- Hooks: `after_create`, `before_run`, `after_run`, `before_remove` (shell).
- Prompt: the template body; Codex skills in the target repo.
- Spec extensions: HTTP server (§13.7), SSH workers (Appendix A), humanised event summaries
  (§13.6); the spec says "Unknown keys SHOULD be ignored for forward compatibility" (§5.3).

## 10. Comparison against the Tailrocks manager concept

Our concept: per-host `jackin` daemon (monitors containers, executes tasks) + a task system where a
human-authored roadmap is decomposed into small tasks, each in its own folder with `TASK.md`,
`task.toml` (dependencies, role) and `verify.sh` that must print `status: DONE`; one isolated agent
container per task; parallel where dependencies allow; daemon verifies and reports.

| Q | Open question | What Symphony does | Applicability / adopt or reject |
|---|---|---|---|
| Q-003 | Where task state lives: files on a git branch vs. service/DB | **Tracker is the state store**; orchestrator state is deliberately in-memory and rebuilt from the tracker + workspace dirs on restart (`SPEC.md` §2.1, §14.3). No DB, no state files in git. The `WORKFLOW.md` policy is in git, but task state is not. | Partially adopt. Their strongest lesson is "one external authority for claim state, rebuildable on restart, no DB." Our `TASK.md`/`task.toml` in a git branch already gives the durable *definition*; we still need a runtime *claim/status* authority. Files-in-git alone cannot do atomic claims across hosts (Symphony sidesteps this by being single-orchestrator). Recommend: task definitions in git; runtime status (claimed/running/blocked/verified + attempt count + host) in the task-system service, treated as rebuildable cache like Symphony's `running`/`claimed` maps. Reject storing status by committing to the branch: Symphony's continuous re-poll/reconcile model (every tick) is far easier against a queryable service than against git history. |
| Q-004 | How dependencies are declared | In the tracker (`blocks`/`blockedBy` links). Orchestrator is DAG-blind; adapters collapse blockers into `dispatchable` and only while the issue is in `Todo` (`linear/client.ex` lines 500-512; `SPEC.md` §4.1.1). No topological sort, no fan-in. | Reject their model; keep `task.toml` `depends_on`. Their design is a consequence of trackers' weak relation semantics, not a recommendation. Two things worth copying: (1) blocker check happens *at dispatch time only*, never mid-run, which is simple and correct; (2) re-evaluate on every poll rather than caching the DAG, so humans editing dependencies take effect immediately. Add: a dependency is satisfied only when the upstream task's `verify.sh` has printed `status: DONE` *and* its result is merged/visible to the downstream workspace, a notion Symphony lacks. |
| Q-005 | Who decomposes | Humans, in the tracker. Agents may file follow-ups into `Backlog`, which never auto-dispatches (`elixir/WORKFLOW.md`). | Adopt the guardrail: agent-proposed tasks land in a non-dispatchable state (`proposed/` folder or `status = "proposed"` in `task.toml`) until a human promotes them. This is the single cheapest control against runaway self-generated work. |
| Q-006 | How verification is trusted | Not verified by the system. Agent self-reports in a workpad comment; CI and a human reviewer are the gates; approval is a human moving the ticket to `Merging` (`SPEC.md` §1, §11.5; `elixir/WORKFLOW.md`). | Our `verify.sh` run by the daemon is strictly stronger and should stay. Adopt from Symphony: (a) ticket-authored acceptance criteria are "non-negotiable acceptance input" that the agent must mirror into its plan, so `TASK.md` acceptance criteria should be the *source* of `verify.sh`, not a parallel artefact; (b) the "Completion bar" concept as an explicit checklist. Reject: relying on the agent's own claim of green tests. Note Symphony's warning that hooks "are fully trusted configuration"; our `verify.sh` is authored per task, possibly by an agent, so the daemon must run it in the *same* isolated container with no extra privileges and treat its stdout as data, not as a command. Consider a second, human-owned repo-level verifier (like `make all` in their CI) that agents cannot edit. |
| Q-007 | How parallel results merge | One PR per issue against `main`; the agent merges `origin/main` into its branch (`pull` skill), resolves conflicts itself, and squash-merges via the `land` skill only after a human moves the ticket to `Merging`. Serialisation via `max_concurrent_agents_by_state`. No integration branch, no merge queue. | Adopt the mechanism (agent rebases/merges on latest trunk before handoff; conflict-resolution guidance in `pull` skill is reusable verbatim) but not the topology. With dependencies declared explicitly we can do better: downstream tasks should start from the merged upstream result, so merging must be *part of* task completion (verify → merge to integration branch → mark DONE), not a separate human-triggered state. Keep a human gate before trunk if desired, but at roadmap/milestone granularity, not per task. |
| Q-008 | Failure/retry policy | Exponential backoff `10s·2^(n-1)` capped at 5 min, **unbounded** attempts while active; stall kill after 5 min silence; workspace reused; `attempt` passed to prompt; separate 1 s "continuation" retry after clean exit (`orchestrator.ex` lines 1232-1243; `SPEC.md` §8.4). Blocked state for input-required. | Adopt backoff formula, stall detection, and passing `attempt` + last error into the brief. Reject unbounded retries: add `max_attempts` in `task.toml` (default e.g. 3) after which the task enters `needs_human`. Adopt their distinction between failure classes (§14.1: config vs. workspace vs. agent vs. tracker) because retrying a config error is pointless. Reject reusing the workspace across retries by default: a fresh container per attempt is cleaner and matches our isolation goal; allow opt-in resume. |
| Q-009 | Human escalation | Agent moves ticket to `Human Review` with a "blocker brief"; orchestrator marks input-required sessions `blocked` (in-memory only); no notifications (`elixir/README.md`; `orchestrator.ex` `block_issue_from_entry/4`). | Adopt the structured blocker brief (what is missing / why it blocks / exact human action) as a required field when a task enters `needs_human`. Reject in-memory-only blocked state; persist it. Add notifications (their gap). Adopt the "GitHub is not a valid blocker; try fallbacks first" style rule as a pattern: enumerate what the agent may *not* escalate about. |
| Q-010 | Resource limits | Slot counts only: global, per tracker state, per SSH host. Timeouts: turn silence 1 h, stall 5 min, hook 60 s, `max_turns` 20. No CPU/RAM/disk/token budgets (`config/schema.ex`). | Adopt per-state/per-role concurrency caps (e.g. cap `merging` at 1) and `max_turns`. Our container model lets us add real cgroup limits and a per-task token budget in `task.toml`, which Symphony cannot express; do so. Their token-accounting doc (`elixir/docs/token_accounting.md`) is directly reusable if we ever drive Codex app-server. |
| Q-011 | UI | Terminal TUI + optional LiveView dashboard + tiny JSON API (`/api/v1/state`, `/api/v1/<id>`, `/api/v1/refresh`); history lives in tracker comments; no auth (`router.ex`). Spec explicitly makes UI optional and "MUST NOT be REQUIRED for orchestrator correctness" (§13.4). | Adopt the principle: UI reads a snapshot from the authority and is never on the correctness path. Adopt the snapshot shape (running / retrying / blocked / totals / rate limits, each row with issue URL, session id, last event, tokens, turn count) as the minimum for our daemon's status endpoint. Their "single persistent workpad comment per task" is a good idea for us too: one `PROGRESS.md` (or a status file) per task folder the agent keeps updated, rendered by our UI. |

Cross-cutting takeaways not tied to a single question:

- **Per-host daemon fit**: Symphony's SSH extension is the closest analogue to `jackin`: one
  orchestrator, N hosts, host chosen least-loaded, retries prefer the same host, `workspace.root`
  interpreted on the host, all dispatch waits when hosts are saturated (Appendix A). Its listed
  "Problems to Consider" (environment drift, workspace locality, distinguishing host-connectivity
  failure from in-workspace agent failure "so the same ticket is not accidentally re-executed on
  multiple hosts") are exactly our daemon's problems. Adopt: run identity = (task, host, attempt).
- **Credential brokering**: injecting tracker tools executed host-side and scrubbing token env
  vars from the agent child (`app_server.ex`, `SPEC.md` §10.5, §15.3) is the best pattern in the
  repo. Our daemon should be the only holder of git/PR/task-system credentials and expose them to
  the container as narrow tools or a local proxy, never as env vars.
- **Policy-as-code in the repo**: `WORKFLOW.md` (prompt + runtime config) is versioned with the
  code and hot-reloaded; our `TASK.md` + `task.toml` per task is finer-grained but we lack a
  repo-level "workflow" file for shared agent policy. Add one.
- **Reconcile before dispatch, every tick** (`SPEC.md` §8.1): stop runs whose task was cancelled
  or edited; re-fetch the task before every dispatch to avoid stale decisions. Cheap and prevents a
  whole class of duplicate-work bugs.

## 11. Limitations, risks, and what it does not solve

- **Prototype status**: self-described "engineering preview ... for testing in trusted
  environments"; issues disabled; OpenAI not maintaining as a product. A third-party static
  analysis (https://elixirforum.com/t/openai-just-chose-elixir-to-orchestrate-ai-agents-so-i-ran-their-code-through-mine/74540)
  flags `Orchestrator` (~95 functions) and `StatusDashboard` (~117 functions) as god modules and a
  dependency cycle between `HttpServer`, `Orchestrator`, `StatusDashboard`. This matches the file
  sizes in the clone (`orchestrator.ex` ~1 990 lines).
- **No verification, no planning, no decomposition**: it is a dispatcher. Quality depends on
  "harness engineering" the target repo already has (README; https://openai.com/index/harness-engineering/).
- **Single orchestrator, in-memory state**: no HA, no persistence of retries/blocked map; restart
  re-dispatches everything active, which is safe only because workspaces persist and the prompt
  says "resume."
- **Security posture is deployer's problem**: hooks run unsandboxed with orchestrator privileges;
  default Codex sandbox is workspace-write with no network, but the reference workflow turns
  approvals off and network on; the web API has no auth; `SPEC.md` §15.5 explicitly warns of
  "data leaks, destructive mutations, or full machine compromise" from prompt-injected tracker
  content. Provider tools are scoped by the *token*, not by project ("the tool can access whatever
  the configured Linear token can access", `elixir/README.md`).
- **Unbounded retry and token spend**: no attempt cap, no budget; third-party write-ups note
  "high token consumption" (tessl.io). Any active ticket the agent cannot finish loops every
  ≤5 min forever.
- **Codex-only**; tracker-only intake; no file/API work queue; no multi-repo tasks (one clone per
  workspace, defined by the hook).
- **Merging is serial and human-gated per ticket**; no merge queue or integration branch, so
  parallelism at N agents produces N conflicting PRs that each agent resolves ad hoc.
- **Dependencies are shallow**: only "don't start a `Todo` with a live blocker"; no ordering
  guarantee that upstream code is merged before downstream starts.
- **Observability is live-only**: no run history, no artefact store, notifications absent.
- **Spec drift risk**: the Elixir implementation "may be a superset of the spec" and the spec is
  "Draft v1" (`elixir/AGENTS.md`, `SPEC.md`); e.g. the `blocked` map, `worker`, `server`,
  `observability` keys are implementation extensions.
